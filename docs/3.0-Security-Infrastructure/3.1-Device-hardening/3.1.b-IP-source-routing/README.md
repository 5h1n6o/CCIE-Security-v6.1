# 3.1.b IP source routing

Cisco デバイスのハードニング（要塞化）において、**IP Source Routing** の無効化は、コントロールプレーンおよびインフラストラクチャ保護の基本ステップです。この機能は、パケットの送信者がルータのルーティングテーブルを無視して、パケットが通過すべき経路を明示的に指定することを可能にします。CCIE Security v6.1 においては、デバイスの攻撃面を最小化するための「不要なサービスの停止」の一環として位置付けられています。

---

## 📘 概要

*   **機能概要**: パケットの送信者が IP ヘッダーのオプションフィールドを使用して、目的地に到達するまでに通過すべきルータのリストを指定する機能です。
*   **利用目的**: 本来的にはネットワークのデバッグや診断（特定のパスが生きているかの確認）に使用されます。
*   **どのような場面で利用するか**: 現代のプロダクションネットワークでは、セキュリティ上のリスクが極めて高いため、**原則として全てのデバイスで無効化**します。

---

## 🔑 要点

| 項目 | 内容 |
| :--- | :--- |
| **特徴** | 送信者が経路を決定する（Source-determined routing）。 |
| **用途** | ネットワーク診断、トラブルシューティング（現在はほぼ使われない）。 |
| **メリット** | ルーティングテーブルに依存しない動的な経路確認。 |
| **デメリット** | セキュリティポリシー（Firewall 等）の回避、IP スプーフィングの踏み台に悪用される。 |
| **対応機種** | Cisco IOS, IOS-XE, ASA（デフォルトで無効な場合が多い）。 |
| **制限事項** | 無効化すると、正規のデバッグ目的でのソースルーティングも不可になる。 |
| **設計上の注意点** | インフラ全体で一貫して `no ip source-route` を設定すること。 |

---

## 🏗 動作原理

通常、ルータは自身のルーティングテーブル（RIB/FIB）に基づいてパケットのネクストホップを決定しますが、IP Source Routing が有効な場合、パケット内の **IP Options フィールド** の指示が優先されます。

### ソースルーティングの種類
1.  **Strict Source Routing (SSR)**: 指定されたホストのリストを、記載された順序通りに正確に通過しなければならない。
2.  **Loose Source Routing (LSR)**: 指定されたホストを順に通過する必要があるが、その間に他のルータを経由してもよい。

```text
[ Attacker ] --- (正規のパス) ---> [ Firewall ] --- (ブロック) ---> [ Target ]
      |
      └--- (Source Routing を使用) ---> [ Compromised Router ] --- (迂回パス) ---> [ Target ]
```
※ 攻撃者は IP オプションを使用して、セキュリティチェックを回避する経路を強制できます。

---

## ⚙ 動作シーケンス

1.  **パケット受信**: ルータがインターフェイスで IP パケットを受信する。
2.  **ヘッダー解析**: IP ヘッダーの「Options」フィールドを確認する。
3.  **ソースルートの検出**: LSR (Type 131) または SSR (Type 137) オプションが含まれているか判別。
4.  **転送処理 (有効時)**: オプションで指定された次のホップへパケットを転送する（自身のルーティングテーブルをスキップ）。
5.  **転送処理 (無効時)**: パケットをドロップし、必要に応じて ICMP 宛先到達不能（Destination Unreachable）を送信するか、オプションを無視する。

---

## 🎯 試験対策（CCIE Securityラボ試験）

*   **「不要なサービスの無効化」要件**: ラボ試験の「System Hardening」セクションでは、具体的なコマンド名が指定されず、「デバイスの攻撃面を最小化せよ」「不要な IP サービスを停止せよ」といった抽象的な指示が出る場合があります。その際、`no ip source-route` は必須リストに含まれます。
*   **IP Options の悪用防止**: 脅威の特定と緩和（Threat Identification and Mitigation）の観点から、悪意のある IP オプションの使用を阻止する設定が問われます。
*   **デフォルト設定の確認**: 新しいバージョンの IOS-XE ではデフォルトで無効になっていることがありますが、試験では**明示的にコンフィグに入れる**ことが求められる場合があります。
*   **他のハードニングとの組み合わせ**: `no ip http server`、`no service finger`、`no ip bootp server` 等とセットで設定する習慣をつけてください。

---

## 🛠 設定方法

### 1. Cisco IOS / IOS-XE
グローバルコンフィギュレーションモードで設定します。
```bash
Router(config)# no ip source-route
```

### 2. Cisco ASA
ASA ではデフォルトで無効になっていますが、特定のオプション付きパケットを処理・検査する場合は以下のコマンドに関連します（通常は設定不要、あるいはドロップを維持）。
```bash
# デフォルトでドロップされる。明示的な許可設定がない限り安全。
```

## 🚨 トラブルシュート

| 症状 | 原因 | 確認・対処方法 |
| :--- | :--- | :--- |
| セキュリティ監査で指摘される | `no ip source-route` が設定されていない | <code>show run</code> で設定の有無を確認し、追加する。 |
| 特定の診断ツールが動かない | ツールが Source Routing に依存している | <code>ip source-route</code> を一時的に許可するか、別の診断手法（Traceroute 等）を使用。 |
| パケットが意図せずドロップされる | 経路制御のために Source Routing を使用している | 現代の設計では Policy-Based Routing (PBR) や VRF に移行すべき。 |

---

## ⚠ 制限事項

*   **デバッグへの影響**: ネットワークの特定のパスを手動でトレースする高度なデバッグができなくなります。
*   **パフォーマンスへの影響**: IP オプション付きパケットは通常、ハードウェア（ASIC）ではなくソフトウェア（CPU）で処理されるため、有効にしていると DoS 攻撃の対象になりやすい（CPU 負荷増大）。

---

## 🔄 他技術との関連

*   **CoPP (3.1.a)**: IP オプション付きパケットをコントロールプレーンで制限・ドロップするために CoPP と併用されます。
*   **uRPF (3.3.a)**: 送信元 IP スプーフィング対策として、Source Routing の無効化と組み合わせて多層防御を構築します。
*   **iACLs (3.1.c)**: ネットワーク境界で IP オプションを持つパケットを明示的に拒否する ACL を適用します。

---

## 🧩 比較表

### IP Source Routing vs Policy-Based Routing (PBR)

| 特徴 | IP Source Routing | Policy-Based Routing (PBR) |
| :--- | :--- | :--- |
| **制御者** | パケットの送信者（エンドホスト等）。 | ネットワーク管理者（ルータ設定）。 |
| **セキュリティ** | **低い（攻撃者に制御を許す）。** | **高い（管理者が制御を保持）。** |
| **実装場所** | IP ヘッダーオプション。 | ルータの Route-map 設定。 |
| **推奨される用途** | なし（廃止すべき）。 | 特定トラフィックの経路制御。 |

---

## 💡 ベストプラクティス

1.  **グローバル無効化**: すべてのルータで `no ip source-route` を初期設定に含める。
2.  **境界でのブロック**: 境界ルータ（Edge Router）の ACL で、オプション付きパケットを物理的に遮断する。
3.  **モニタリング**: `show ip traffic` で Source Routed パケットの受信を監視し、攻撃の予兆を検知する。

## 📝 ラボ学習・設定サンプル例

### 1. 基本的なハードニング
*   **要件**: R1 において、送信者が経路を指定できないようにせよ。
*   **設定**: `no ip source-route`

### 2. インフラ保護スクリプトの一部として
*   **要件**: 管理アクセス以外の不要な IP サービスを一括停止せよ。
*   **設定**: 
    ```bash
    no ip source-route
    no ip http server
    no ip finger
    ```

### 3. IP オプションパケットのドロップ確認
*   **課題**: `show ip traffic` を実行し、ソースルートパケットのドロップ数を確認せよ。

### 4. CoPP との連携
*   **要件**: コントロールプレーンに到達する前に IP オプションパケットを破棄せよ。

### 5. IPv6 環境での対応
*   **要件**: IPv6 においても同様のソースルーティング（Type 0 Routing Header）を無効化せよ。
*   **設定**: `no ipv6 source-route`

### 6. リロード後の永続性確認
*   **課題**: 設定を保存し、リロード後も `no ip source-route` が有効であることを確認せよ。

### 7. トラフィック統計のリセット
*   **課題**: `clear ip traffic` を実行後、不正パケットを送信してカウンタが増えるか検証せよ（エミュレータ環境）。

### 8. ACL による補完的保護
*   **要件**: 外部からの IP オプション付きパケットを ACL で拒否せよ。

### 9. 診断ツール（Loose Source Route）の動作不可確認
*   **課題**: Windows の `tracert -j` オプションを使用して、ルータがパケットを拒否することを確認せよ。

### 10. 全インフラデバイスへの一括適用
*   **課題**: EEM (Embedded Event Manager) 等を使用して、設定が削除された場合に自動復旧する仕組みを検討せよ。

## ❓ 想定試験問題

1.  **コンフィグ読解**: デバイスに `ip source-route` が設定されている場合、どのようなセキュリティリスクがあるか？
    *   **回答**: 攻撃者が Firewall や ACL による制御を迂回して、内部ネットワークへアクセスする経路を強制するリスクがある。
2.  **Design**: 管理者以外がパケットの経路を制御することを禁止するための最もシンプルなコマンドは？
    *   **回答**: `no ip source-route`
3.  **トラブルシュート**: セキュリティスキャナが「IP Source Routing Enabled」を検出した。設定を確認すると `no ip source-route` は存在しない（デフォルトのまま）。どう対処すべきか？
    *   **回答**: 明示的に `no ip source-route` を設定し、コンフィグに反映させる。
4.  **実装**: IP Source Routing パケットが CPU に負荷をかけている。CoPP 以外での対策は？
    *   **回答**: インターフェイス ACL またはインフラ ACL (iACL) で IP オプション付きパケットを `deny` する。
5.  **Design**: ソースルーティングパケットがハードウェアで転送されない理由は？
    *   **回答**: IP オプションの解析にはヘッダーの詳細な検査が必要であり、多くのプラットフォームではパンティング（CPU 処理への転送）が発生するため。

## 📝 **補足（Notes）**

*   **学習メモ**: IP Source Routing は、OSPF や BGP といったルーティングプロトコルとは無関係に、**パケット自体に経路情報を持たせる**特殊な機能であることを理解してください。
*   **注意点**: ラボ試験の採点スクリプトは、設定が「あるべき姿」になっているかをチェックします。`no ip source-route` が指示されていなくても、ベストプラクティスとして設定が推奨される場合があります。
